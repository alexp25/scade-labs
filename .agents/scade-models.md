# Scade One models

## Lab 3 — two parallel copies: `src/lab3/starter/` (flat, does not open correctly) and `src/lab3/solution/` (correct project layout, use this as the reference)

Same content, two different directory layouts:

- **`src/lab3/starter/`** — `blocks.swan`/`test.swant` sit flat, as siblings
  of `demo.sproj`, not inside an `assets/` subfolder. **Scade One does not
  discover them there — opening this project in Scade One shows an empty
  project.** This is a known, left-as-is state (per explicit maintainer
  instruction) from when the former Lab 4.1's `assets/blocks.swan` /
  `assets/test.swant` were flattened into `src/lab3/starter/` during the
  Lab 3/Lab 4 merge — the flattening broke Scade One's own directory
  convention. Do not "fix" this without maintainer confirmation; use
  `src/lab3/solution/` instead when you need a project that actually opens.
- **`src/lab3/solution/`** — the same files, correctly laid out
  (`assets/blocks.swan`, `assets/test.swant`, alongside `demo.sproj`,
  `counter_wrapper/`, `limiter_wrapper/`, `setup_wrapper.py`,
  `test_counter.py`, `test_limiter.py`, `test_counter_advanced.py`,
  `test_limiter_advanced.py`, `requirements.txt`). **This is the directory
  to open in Scade One and to point instructors at.** It also contains
  `requirements.md`, the unrelated EARS answer-key file (see
  `.agents/verification.md`) — the two are just different halves of Lab 3's
  reference material sharing a directory, not the same artifact.

Model source `assets/blocks.swan` (Swan `2025.2`/graph `2.1`), hand-authored:
- `function limiter(value_in, min, max: float64) returns (value_out: float64)`
  — diagram-form double clamp. Element-level `#pragma requirement` links
  (the solution copy's Activity 2G answer): `REQ-LIM-01` on the `>max`
  comparison and its if-then-else (upper branch, clamp to max), `REQ-LIM-02`
  on the `<min` comparison and its if-then-else (lower branch, clamp to
  min), `REQ-LIM-03` on the plain `value_in` leaf feeding the innermost
  else (pass-through/otherwise) — matching `requirements.md`'s canonical
  REQ-LIM IDs and Activity 2E's "upper branch / lower branch / otherwise"
  description. `src/lab3/starter/blocks.swan` has the same logic but no
  pragmas — students add these themselves.
- `node counter(init_value, step: int32) returns (count: int32)` — uses
  `pre` + `+` for the running total. Solution copy carries `REQ-CNT-01` on
  the `pre` node (its initial branch is `init_value`) and `REQ-CNT-02` on
  the `+` node (`previous_count + step`), matching Activity 4F's
  "initial-value branch vs. accumulation branch" wording.
- `const init: float64 = 0;`
- Four test scripts, all identical between `starter/` and `solution/` and
  all accepting `--project-dir`/`-d` (default: the script's own folder) so
  a student can run them against a project generated/copied/uploaded
  somewhere else, not just in place:
  - `test_limiter.py`/`test_counter.py` — **simple**: cycle the operator,
    print `[req] ... PASS/FAIL` per test case. No `blocks.swan` parsing.
  - `test_limiter_advanced.py`/`test_counter_advanced.py` — same tests,
    plus the traceability tooling: parse `blocks.swan` for
    `#pragma requirement` pragmas at runtime (plain regex/brace-matching
    over the text, no Scade One API involved), print which node ID(s) each
    REQ resolves to before running the cycle assertions (see
    `.agents/verification.md`), then write
    `<project-dir>/results/<operator>_traceability.csv` (one row per test
    case) and render `<project-dir>/results/<operator>_diagram.png` with
    `matplotlib`: one box per parsed diagram node, positioned using the
    node's own `"xy"` pragma coordinates and colored green/red by whether
    its linked requirement's test case(s) passed or failed (gray if the
    node has no requirement link) — a custom stand-in for the coverage
    report/colored-diagram view Scade One Student Edition doesn't provide.
    `requirements.txt` lists `matplotlib` for this; the scripts still run
    and print PASS/FAIL without it, just skipping the diagram with a note.
    `docs/lab3/img/limiter_diagram.png` and
    `docs/lab3/img/counter_diagram.png` are committed copies of this
    output, referenced from `docs/lab3/lab.md` Activity 7G.
  - The committed `src/lab3/solution/results/` directory holds this
    session's reference output (matches Lab 4's convention of committing
    `results/` as reference material) — regenerate by running the
    `_advanced` scripts from `src/lab3/solution/`.

Test harness `assets/test.swant` — hand-authored, **populated**: two
`_harness` blocks (`harness_counter`, `harness_limiter`), each instantiating
the operator under test (`#pragma swt under_test`) with fixed input
constants and a `_stop_condition` wired to `false`.

`counter_wrapper/counter_wrapper.py`, `limiter_wrapper/limiter_wrapper.py`
— **generated** (`# generated by PyScadeOne Wrapper 1.0`). Do not hand-edit;
regenerate via `setup_wrapper.py` (requires local Scade One), in whichever
of the two directories you're working from.

## Lab 4 — `src/lab4/starter/CruiseControl/`

Three packages, three different roles — `docs/lab4/lab.md` now has a
"Project Structure" section spelling this out for students:
- `CC_design` (`cruise_control`/`regulator`/`limiter`) — **the deliverable**:
  the only node with real-world scope, the only one Part 6 generates code
  from.
- `Car_design` (`car`) — a plant-model stand-in for a real vehicle, provided
  only so students have something to drive the controller against; not
  modified by students, not a code-generation target.
- `Simulation` (`main`/`main_manual`) — wiring nodes that connect
  `cruise_control` to `car` purely for interactive/manual simulation; never
  targeted by the Part 6 code-generation job, would not appear in a shipped
  system.

- `CruiseControl.sproj` — plain JSON manifest, declares one Resource:
  `{"Kind": "SimulationData", "Path": "resources\\main_inputs.sd", "Key":
  "main_inputs"}`.
- `assets/CC_design.swan` — hand-authored:
  - `node cruise_control(v_speed, brake, accel, on, res, set_point: ...)
    returns (throttle: float32)`, annotated `#pragma requirement reQ2` (the
    **only** requirement-traceability pragma in the file — see
    `.agents/verification.md`). Contains a **nested automaton**: outer
    `cc_disabled` (initial) / `cc_enabled`; `cc_enabled` contains an inner
    automaton `cc_active` (initial) / `cc_standby`. Transitions: `on` moves
    disabled→enabled; `brake>10.0 or accel>10.0` moves active→standby;
    `res and brake<10.0` moves standby→active.
  - `node regulator(set_point, speed: float32) returns (throttle: float32)`
    — PI-style: proportional term (`0.5*error`) + integral accumulator via
    `pre` (gain `0.2`), then two `limiter` instance blocks clamp the
    pre-limiter sum to `[-100,100]` and the final throttle to `[0,100]`.
  - `node limiter(input, upper_limit, lower_limit: float32) returns (output:
    float32)` — same clamp pattern as Lab 3's `limiter`, float32/`node`
    form.
- `assets/Car_design.swan` — hand-authored vehicle plant model:
  `node car(throttle_percent, brake: float32) returns (speed, rpm: float32;
  gear: int32)`. Gear selection via a `case` construct over speed thresholds
  (20/40/70/100/130 km/h), rolling/drag/brake force constants, `pre`-based
  speed integration.
- `assets/Simulation.swan` — hand-authored, wires `Car_design` + `CC_design`
  together: `node main(...)` (closed-loop, feeds car speed back into cruise
  control) and `node main_manual(...)` (open-loop, `throttle_percent =
  accel*100.0`, no cruise control — for plant-only exploration).
- No `.swant` test-harness file ships in this package at all (an earlier,
  empty `Main_test.swant` scaffold has since been removed). `docs/lab4/lab.md`
  no longer describes test-harness-building activities for this lab (Part 5
  only briefly mentions Scade One test harnesses before redirecting to the
  Python evaluation script in Part 6).
- `cc_wrapper/cc_wrapper.py`, `cc_wrapper.c`, `cc_wrapper.def` — **generated**
  (banner line 1 of each). `cc_wrapper.dll` — **compiled binary, not
  inspectable**; verified only: 94,820 bytes, PE32+ DLL (x86-64, Windows).
- `cc_wrapper/swan_config.h` — Ansys-copyrighted vendor runtime header (no
  generator banner, but explicit `Copyright (c) 2023-2024 ANSYS, Inc.` notice
  and no student-facing edit activity references it) — treat as vendor code,
  not student/instructor source.
- `cc_wrapper/py_wrapper_files.txt`, `cc_wrapper/swan_cg_files.txt` —
  generator-produced manifests listing the wrapper's own output files and the
  underlying C codegen job's output file set, respectively. The `.c`/`.h`
  files listed in `swan_cg_files.txt` (e.g. `main_CC_design.c`,
  `car_CC_design.c`) are **not checked into this directory** — only the
  manifest is.
- `resources/main_inputs.sd` — **binary/opaque, not inspectable as text**:
  465 bytes, magic bytes `S1SDJ` + compressed data; visible embedded strings
  (`brake`, `accel`, `on`, `res`, `set_point`) match the `cruise_control`
  input names, consistent with a saved simulator "SimulationData" resource.

## Verified tooling assumptions (quoted, not inferred)

- Swan/graph format: `-- version swan: 2025.2 graph: 2.1` (identical header
  in every `.swan`/`.swant` file; `.swant` files add `swant: 1.1`).
- Scade One install path used by both labs' scripts:
  `C:\Program Files\Ansys Inc\v261\Scade One Student\Scade One` (implies
  Scade One **v261**; no separate product version string found anywhere).
- Python: `py -3` required (used consistently in `setup_wrapper.py`,
  `generate_python_wrapper.bat`, and both labs' `lab.md`).
- Wrapper generator self-identifies as `PyScadeOne Wrapper 1.0`.
- `docs/lab3/lab.md` itself warns: "The exact class name and instantiation
  method depend on your Scade One version and project name — check the
  generated wrapper file" — i.e. the repo's own authors acknowledge version
  drift risk in the generated wrappers.
